# 设计说明

## 问题与根因

Markdown 无序列表 `-`、`*`、`+` 会被解析为 `<ul>`，浏览器默认 `list-style-type` 为 `disc`，于是 GitHub、多数聊天客户端和 Markdown 转 Word 的链路都会显示为黑色圆点。

根因在结构映射，不在字符本身。因此把 `-` 换成 `*` 或 `+` 无效：三者都生成 `<ul>`。把圆点改成短横线只能靠样式覆盖，而 GitHub 全局 CSS 改不了、聊天客户端也管不到，Word 更是另一套渲染体系。

本项目选择在内容生成源头约束结构，得到三个可验证的好处：源文件在任何渲染器下都一致；不需要依赖平台样式；校验只需扫描文本，不必渲染。

## 结构选择

| 内容语义 | 结构 | 理由 |
| --- | --- | --- |
| 解释与论证 | 段落 | 圆点会切断本应连贯的推理 |
| 步骤与优先级 | 编号列表 | `<ol>` 不产生 disc，且天然表达顺序 |
| 同构字段 | 表格 | 比项目符号更易扫读和比对 |
| 无顺序短项 | 独立段落 | 保持可读性且不引入 `<ul>` |

编号列表与表格是本约定的保留项，不是替代品。禁止无序列表不等于禁止列表：`<ol>` 和 `<table>` 都正常渲染，且承载了更强的语义。

## 竞品调研结论

对 12 个候选包做了范围比对，没有可以直接安装的对口方案：它们或面向通用 Markdown 风格检查，或面向演示文稿与长文排版，覆盖不到“只禁无序列表、三场景分别修”这个窄口。

可借鉴之处有两处。`beamer-academic` 的思路是禁用 `itemize` 而保留 `enumerate` 编号，与本项目“只砍无序、保留编号”的取舍一致。`humanize-text` 附带了校验脚本，但它混合了语言风格检查；本项目只取“可自动校验”这一形式，把规则收窄到只盯 `UL`，不引入任何润稿判断。

未采用的做法包括：全局 CSS 覆写（越界且不可迁移）、渲染后修补（晚于问题发生）、以及把项目符号替换为其他 Unicode 符号（只是换了个圆点）。

## 校验器设计

校验器是只读的，不做自动改写。自动替换无法区分“步骤”“对比”和“叙述”，机械替换会把编号语义和表格结构压平，因此修复必须依据 `references/scenarios.md` 做语义判断。

判定只针对真正的列表语法，以下都不算命中：编号列表、表格分隔行 `| --- |`、分隔线 `---` / `* * *`、行内 `*强调*`、转义字符 `\-`、围栏代码块（含引用块内的围栏）和缩进代码块。任务列表 `- [ ]`、引用块中的列表、以及编号项下的嵌套无序列表都算命中。

退出码约定为 `0` 通过、`1` 命中、`2` 输入错误。`--allow` 对应“用户明确要求保留无序列表”的单次覆写：仍打印全部命中，只把退出码降为 `0`，避免例外被静默吞掉。

## 边界

本项目不处理语言风格、不判断事实、不替代文档排版工具、不修改任何网页样式，也不承诺聊天客户端支持表格。超出这些边界的需求应交给对应工具，而不是把责任塞进格式约定。
