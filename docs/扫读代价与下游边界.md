# 扫读代价与下游边界

本短文说明两件事：禁掉 Markdown 无序列表之后，正文可能更难一眼扫读；以及本 Skill / 脚本管不到哪些下游表现。规则细节与「不管」清单仍以 [`规则与边界.md`](规则与边界.md) 为准。Muse / WorkBuddy 宿主要点见 [`宿主适配-Muse与WorkBuddy.md`](宿主适配-Muse与WorkBuddy.md)。

## 扫读代价

禁止面向读者的无序列表与任务列表之后，同级短项只能改成普通段落、编号列表，或放进表格。段落会拉长篇幅，编号会暗示顺序，表格在部分聊天气泡里又可能折行难看。换来的是：GitHub 预览和许多聊天气泡少一层圆点，条目更容易被逐条引用。这是观感与扫读之间的取舍，不是「可读性一定变好」。

产品文档、会议纪要、参数清单等强列表体裁，合规写法往往要靠小节标题与表格重组，工作量会上升。这是体裁取舍，不是脚本或 Skill 的缺陷。若用户当次明确要求保留 bullet，可按 `SKILL.md` 例外留下普通无序列表；任务列表仍禁止。例外只覆盖当次普通无序列表，不延续到之后对话。

## 管不到的下游

本 Skill 约束的是模型写出的 Markdown 语法层（行首 `-` / `*` / `+` 加空白的无序列表，以及任务列表）。它不转换 HTML 的 `<ul>` / `<li>`，不改网页或聊天客户端的 CSS，也不管粘贴进 Word 之后由 Word 自动加上的项目符号或编号。一篇在 Markdown 源稿里已经干净的正文，贴进 Word 再点一次「项目符号」，前面的约束不会跟着生效。界面上的圆点也不一定来自列表语法（例如装饰用的 `•` / `·` 是普通字符）。

### 下游 Word（操作注意）

1. 先准备**已经没有** Markdown 无序列表的正文（模型侧先按约定写，再用 `--check` 核验）。
2. 粘贴进 Word 时选「只保留文本」（Keep Text Only），避免把源里的列表样式一并带入。
3. 若粘贴后仍出现圆点，须取消该段的**项目符号 / 编号属性**；只删掉圆点字符、不清除列表属性，往往不够，下次编辑还可能回来。
4. 需要 Word 侧核验时，可另用可选脚本 `check_docx_numbering.py`。它不是本 Skill 的强制门禁；退出码与剥除器不同（已对脚本核对：`0` 未发现 bullet 编号链路，`1` 发现，`2` 错误），不可混读。

### 剥除不等于语义等价

1. 必须一开始就按规范写（段落 / 编号 / 表格），不要指望先写出无序列表再靠脚本「救」成终稿。后处理只动标记，救不了结构与语义。
2. `--check` 或改写路径在退出码为 `1` 或 `2` 时，不要把 stdout 里的改写结果直接当终稿；先看 stderr / `--report`，补围栏、抑制区边界或其它跳过原因后再处理。
3. 去掉列表标记后，续行缩进有可能在重解析时被当成缩进代码块；冒号后的裸并列在视觉上也可能「断掉」。风险点到为止：以规范写作为主，不要依赖剥除结果二次排版。

### 模型正文通过线

模型可见正文要通过，须**同时**满足：

1. `python scripts/strip_md_ul.py --check`（可加 `--report`）退出码为 `0`；
2. 报告 `stripped=0`（源稿本身已无待剥无序列表，不是「剥完才干净」）；
3. `summary.suppression_blocks == 0`。

抑制注释不能用来藏列表混过检查：正文里出现抑制指令，模型交付即不算通过。人工维护的源文件仍可按规范使用抑制区；那与「模型正文通过线」不是同一口径。
