# 三场景实操

本文件写可执行的步骤。读者应能据此分清黑点从哪来、禁什么、留什么，以及 GitHub、聊天、Word 各自怎么处理。「几分钟能看懂」是文案目标，不是计时验收。

固定提示词、通过线和宿主字段在文末。三处场景都用同一条通过线，不另设肉眼标准。

## 1. GitHub / Markdown 源码

目标是让 `.md` 源文件本身没有待剥的 UL。README、Issue 草稿和文档源稿都直接写段落、编号列表或表格。

1. 打开要改的 Markdown 源码，不要只看网页预览。
2. 把并列内容改成下面三种之一：编号列表（`1.` `2.` `3.`）、字段对齐的表格、或连续短段落。
3. 代码示例放进已闭合的围栏。围栏里的列表标记是示例，不要为了「看起来干净」去改栏内原文。未闭合的围栏会导致脚本把开栏之后的全文都跳过。
4. 不要修改 GitHub 网站的 CSS，也不要依赖浏览器插件。
5. 提交或打开预览之前，在仓库根目录对源文件执行：

```bash
python scripts/strip_md_ul.py --check path/to/file.md
```

stderr 里 `stripped=0` 且退出码为 `0`，表示这份源文件没有待剥 UL。人工源稿可以保留抑制区，这里不要求 `suppression_blocks` 为 0。若 `stripped` 大于 `0`，退出码仍可能是 `0`，因为 `--check` 沿用改写结果的退出码：能剥干净就是 `0`。这时若你想直接得到剥过的正文，用默认模式并把标准输出重定向到一个新文件，看完再决定是否替换。退出码 `1` 的输出是未完成结果，不要提交。

## 2. AI 聊天

目标是在发送前控制消息源码，而不是等某个客户端把圆点画出来再改。

1. 按 `skills/no-markdown-bullets/SKILL.md` 里的路径，把整个 `skills/no-markdown-bullets/` 目录手工复制到宿主的 Skills 目录。Cursor 项目内路径是 `<项目>/.cursor/skills/no-markdown-bullets/SKILL.md`，用户目录是 `~/.cursor/skills/no-markdown-bullets/SKILL.md`。这两处的发现结果都还是待验证。
2. 新开对话，先让宿主列出当前可见的 Skill。确认名单里有 `no-markdown-bullets` 之后，再用文末的固定提示词显式要求按该约定作答。只看到一次没有圆点的回答，不能代替这一步。
3. 短回答用自然段。需要逐步执行或逐条引用时用编号。只有确认这个客户端能显示表格、而且列数不多时才用表格；否则每条一个编号，写成「字段：值」。
4. 若回答里仍然出现行首 UL，把模型可见正文整篇存成一个文件，再运行：

```bash
python scripts/strip_md_ul.py draft.md > draft.stripped.md
```

先看退出码和 stderr，再决定要不要用 `draft.stripped.md`。不要只剪其中一个段落就宣称整篇通过。宣称模型正文通过，仍要用文末通过线：退出码 `0`、`stripped=0`，且没有抑制区。
5. 用户当次明确要求保留 bullet 时，这一次普通 UL 可以留下，不要对这一次输出运行脚本。任务列表仍然要改成纯文本，脚本也没有保留勾选框的开关。

## 3. Word / WPS

目标是不要把 Markdown 无序列表粘成 Word 的自动项目符号。脚本改的是文本标记，取消不了已经写进文档的项目符号属性。

1. 在聊天或编辑器里准备好没有 UL 的正文。需要条目时，优先用编号或短段落。
2. 复制这段正文。
3. 在 Word 中粘贴时选择「只保留文本」。入口一般在粘贴选项或「选择性粘贴」里。WPS 里对应无格式粘贴或粘贴为纯文本。菜单名称随软件版本变化，本文件不绑定某一个 build。
4. 若圆点已经出现：选中这些段落，在「开始」选项卡中取消项目符号。不要只把圆点字符删掉却留下列表属性，下一次回车可能又冒出来。
5. 需要结构化条目时，用 Word 或 WPS 自己的编号，不要从聊天窗口直接粘贴带 `- ` 的 Markdown，也不要把 Markdown 表格当成已经变成了 Word 表格。
6. 文件已经是 `.docx` 时，可以用 `python scripts/check_docx_numbering.py 文件.docx` 查看哪些段落解析成了 bullet 编号。这个检查器和 `python-docx` 都是**卫星（可选，不进 Skill 验证主路径）**。它只读，不改文件。退出码和剥除器不同：`0` 表示没有 bullet 编号，`1` 表示发现了，`2` 表示文件读不了。编号列表（decimal）不报。运行它不需要安装 python-docx；那个包只在可选测试里使用。

## 固定提示词与通过线

宿主：Cursor（放置路径见上，发现与强制执行待验证）。模型：待验证。版本：待验证。

下面三句是固定提示词，验收时原样使用，不要临时改写：

1. 请用普通段落说明 Markdown 无序列表为什么会在预览里变成圆点。不要使用项目符号。
2. 请写出把这段文字粘贴到 Word 之前的三步操作，使用编号列表。
3. 请用表格对比段落、编号列表、表格这三种写法。列：场景、写法、会不会变成 disc 圆点。

通过线预先写死，按解析后的 UL 节点计数：

1. 只取模型的可见正文，不含额外加上的批注。
2. 执行 `python scripts/strip_md_ul.py --check 输出.md`。要看 `summary.suppression_blocks` 时加上 `--report -` 或 `--report report.json`。
3. 通过：`--check` 退出码 `0`，且 `stripped=0`，且模型正文没有抑制区。看 `--report` 时 `summary.suppression_blocks` 为 `0`；不看报告时，正文里不能出现 `no-markdown-bullets:`。
4. 不通过：退出码为 `1` 或 `2`，或 `stripped` 大于 `0`，或模型正文里开了抑制区。
5. 围栏、YAML front matter、表格、缩进代码内部的标记不计入。人工源文件仍可使用抑制区；这条通过线只约束模型正文。脚本默认仍保留抑制区内的原文。
6. 截图里没有黑点，不算通过。
7. 不承诺任意助手或任意模型达到 100%。

## 明确不做

1. 不修改其他插件仓库，也不依赖它们。
2. 不在本仓库写别的工具能否安装的结论。
3. 不改 GitHub 的 CSS，不做浏览器插件或 Word 插件。
4. 不做文风润色，也不发布 npm 命令行包。
