# 三场景修复与迁移规则

## 统一判断

先按内容语义选结构，不按原列表符号做字符替换。

| 内容语义 | 首选结构 | 不适用时的替代 |
| --- | --- | --- |
| 解释、论证、连续结论 | 普通段落 | 按主题拆成多个段落 |
| 操作步骤、时间顺序、优先级 | 编号列表 | 带小标题的分段 |
| 同构字段、配置项、方案对比 | 表格 | 每项一个编号条目 |
| 无顺序的简短并列项 | 独立段落或编号列表 | 表格 |

编号不代表内容一定有序；当编号只用于引用条目时，也可以使用，但不要虚构优先级。

## GitHub Markdown

目标是让 `.md` 源文件本身符合约定。README、Issue 草稿、讨论内容和文档站源稿都直接采用段落、编号列表或表格。

将已有的无序列表改为其他结构时，保留嵌套关系：子项可改写为父编号下的段落，或使用 `1.1`、`1.2` 这类仅在原内容已有该编号体系时使用的编号。不要为嵌套内容虚构新的层级。

以下情况不是无序列表，不应误改：Markdown 表格分隔行、`---` 或 `* * *` 分隔线、行内 `*强调*`、编号列表、围栏代码块和缩进代码块中的示例。

本 Skill 不修改 GitHub、浏览器或文档站的全局 CSS。样式覆写既管不住聊天和 Word，也会让仓库表现依赖外部环境。

## 聊天消息

目标是在发送前得到符合约定的消息源稿，而不是依赖某个客户端的渲染结果。

短回答优先使用自然分段。需要逐项核对、执行或引用时使用编号列表。只有客户端明确支持 Markdown 表格且列数较少时才使用表格；否则把每行改为一个编号条目，字段写成“字段：值”。

发送前可将消息文本通过标准输入交给校验器。代码示例应放在围栏代码块中，校验器不会把代码块里的列表语法当作正文违规。

## Word 文档

目标是生成原生 Word 内容，而不是把含无序列表的 Markdown 粘贴或转换后再修圆点。

叙述内容映射为正文段落，步骤映射为原生编号列表，同构字段映射为原生表格。使用当前文档工具提供的段落、编号和表格能力，不用连字符模拟列表，也不把 Markdown 标记写入正文。

已有 Word 文件需要修改时，只调整由 Markdown 无序列表产生的目标段落；保留其他样式、编号和表格。此 Skill 不负责全文排版或语言润色。

## 明确覆写

用户可以针对某次回答、某份文件或某条消息明确要求 Markdown 无序列表。此时按用户指令输出，并在后续内容恢复默认约定。示例：“这份兼容旧流程的 README 可以保留无序列表”只允许该 README 保留，不代表以后所有文档都允许。

`--allow` 只改变校验退出码，不隐藏命中。它适合已有明确例外的文件进入批量检查时使用，不适合作为默认命令。
